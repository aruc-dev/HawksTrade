## 1. Why This Is The Top Priority

Today the entire HawksTrade evidence base is **one 12-month backtest window ending 2026-04-29**. That window happened to cover a generally bullish, tech-led regime. The reported +20.70% / -1.92% drawdown / 53.6% win rate over 112 trades is a real result, but it is statistically *one observation* of how the system performs.

Walk-forward validation across multiple historical regimes is the cheapest and highest-impact discipline that:

1. **Quantifies regime sensitivity** — tells you what happens in a 2022-style bear or a 2020-style crash.
2. **Catches overfitting** — a strategy that only works in the recent window will fail walk-forward.
3. **Defines the *forward expectation*** — the worst window in walk-forward is roughly the realistic worst case, not the headline number.
4. **Becomes a code-enforced gate** — capital does not scale unless walk-forward passes. This removes the human "but the last quarter was great" failure mode.

The codebase already has `scheduler/run_walkforward.py` — this plan extends it to be a **production gate**, runs it across the regimes that matter, and embeds it in the change-control workflow.

## 2. Acceptance Criteria

This plan is "done" when **all** of the following are true:

- [ ] A committed report at `reports/walkforward_master.md` shows ≥6 non-overlapping 180-day windows spanning at least 2019-01-01 → most recent month.
- [ ] At least one window in the report covers each of: 2020 COVID crash, 2022 tech bear, 2024 chop/election, current regime.
- [ ] The report is regenerated by a single command: `python3 scheduler/run_walkforward.py --profile master`.
- [ ] Pass criteria are configured in `config/config.yaml` under `validation.walkforward` and enforced in `run_walkforward.py` (currently thresholds are CLI args only).
- [ ] **≥66% of windows pass at 30 bps round-trip slippage** (15 bps slippage per side + 5 bps fee per side = 40 bps round-trip cost — use the stress level, not the headline).
- [ ] CI / pre-commit hook runs an abbreviated walk-forward (3 windows) on any change to `strategies/*.py`, `core/risk_manager.py`, `core/exit_policy.py`, or `config/config.yaml` strategy sections.
- [ ] CHANGELOG entry documents the gate and the policy: "capital does not scale unless `walkforward_master` passes at the configured threshold."
- [ ] Stop-the-line policy is documented: when walk-forward regresses below threshold, all new entries pause until the regression is explained.

## 4. Window Definitions

Six minimum windows, each 180 trading days, **non-overlapping**, each ending on a date that captures a distinct regime. Add more if data is available.

| # | Window end | Regime context | Why included |
|---|---|---|---|
| 1 | 2019-12-31 | Calm bull, low vol | Baseline normal-market behaviour |
| 2 | 2020-09-30 | COVID crash + V-recovery | Crash and recovery regime |
| 3 | 2021-12-31 | Stimulus-driven rip, late-cycle | Trending bull with high participation |
| 4 | 2022-12-31 | Rate-hike tech bear | Sustained downtrend — the failure mode |
| 5 | 2023-12-31 | SVB shock + AI rip | Mid-cycle reversal regime |
| 6 | 2024-09-30 | Pre-election chop | Range-bound regime |
| 7 | most recent − 60 days | Current regime | Recency check (excludes locked OOS) |

The most recent 60 days remain a **locked out-of-sample window** — never used for tuning or refresh, only for final validation.

**Data caveat to document loudly:** if Alpaca historical data does not extend back to 2019 for all symbols in the universe, the report must explicitly list which symbols had truncated histories per window. A naïve "missing data → skip symbol" causes silent universe shrinkage and is itself a form of bias.

## 5. Pass Criteria

Per-window pass criteria, configured in `config/config.yaml`, default values:

| Metric | Baseline (15 bps cost) | Stressed (30 bps cost) | Severe (50 bps cost) |
|---|---:|---:|---:|
| Return (annualised) | ≥ +4% | ≥ 0% | ≥ -2% |
| Max drawdown | ≤ 8% | ≤ 10% | ≤ 12% |
| Profit factor | ≥ 1.20 | ≥ 1.00 | ≥ 0.90 |
| Min trades | ≥ 25 | ≥ 25 | ≥ 25 |
| Daily Sharpe | ≥ 0.50 | ≥ 0.20 | n/a |

Aggregate pass criteria:

- **Baseline (15 bps):** ≥ 80% of windows pass.
- **Stressed (30 bps):** ≥ 66% of windows pass. **← THIS IS THE BINDING CONSTRAINT FOR CAPITAL SCALING.**
- **Severe (50 bps):** ≥ 50% of windows pass.
- **Locked OOS window:** must pass at stressed cost.

These thresholds are deliberately less strict than the single-window production gate (which requires +10% return on the 12-month) because walk-forward includes bad regimes. A strategy that returns +20% in a bull and -5% in a bear has a positive average — that is the realistic forward expectation.

## 6. Work Breakdown

### Week 1 — Foundation

**Task 1.1 — Add `validation.walkforward` config schema.** [4h]
Extend `config/config.yaml` with:
```yaml
validation:
  walkforward:
    enabled: true
    profiles:
      master:
        window_days: 180
        windows:
          - end_date: "12/31/2019"
            label: "calm_bull_2019"
          - end_date: "09/30/2020"
            label: "covid_crash_2020"
          # ... etc.
        cost_levels:
          - { name: baseline, slippage_bps: 7.5, fee_bps: 5.0 }
          - { name: stressed, slippage_bps: 15.0, fee_bps: 5.0 }
          - { name: severe,   slippage_bps: 25.0, fee_bps: 5.0 }
        thresholds:
          baseline:  { min_return_pct: 0.04, max_drawdown_pct: 0.08, min_profit_factor: 1.20, min_trades: 25, min_daily_sharpe: 0.50 }
          stressed:  { min_return_pct: 0.00, max_drawdown_pct: 0.10, min_profit_factor: 1.00, min_trades: 25, min_daily_sharpe: 0.20 }
          severe:    { min_return_pct: -0.02, max_drawdown_pct: 0.12, min_profit_factor: 0.90, min_trades: 25 }
        pass_rate:
          baseline: 0.80
          stressed: 0.66
          severe:   0.50
        oos_lock:
          end_date: "auto"  # most recent − 60 days
          must_pass_at: stressed
```

**Task 1.2 — Extend `run_walkforward.py` to read profiles from config.** [6h]

**Task 1.3 — Per-strategy attribution in the report.** [4h]

**Task 1.4 — Unit tests for profile loading and threshold evaluation.** [3h]

### Week 3 — Integration and governance

**Task 3.1 — Pre-commit hook (advisory, not blocking initially).** [3h]
Hook fires on changes to `strategies/*.py`, `core/risk_manager.py`, `core/exit_policy.py`, `config/config.yaml`. Runs `run_walkforward.py --profile quick`. Posts the result inline. Does not block commit for the first month; promote to blocker once stable.

**Task 3.2 — Update `CLAUDE.md` with the mandatory pre-scaling step.** [1h]
Under "Switching from Paper to Live" (section 13), add a new prerequisite: "Master walk-forward must pass at the stressed cost level within the last 30 days. The report at `reports/walkforward_master.md` must be regenerated and committed."

**Task 3.3 — Update `backtests.md`** to point to the master walk-forward report as the canonical evidence source rather than the single 12-month number. [1h]

**Task 3.4 — Stop-the-line policy.** [2h]
Documented in `CLAUDE.md`: when a regenerated `walkforward_master` falls below threshold, the agent must (a) pause any "scale capital" or "enable strategy" actions, (b) file a beads issue with the regression details, (c) revert the change that caused the regression or pause new entries until human review. This is a procedural change; the enforcement is via documented mandatory workflow.

**Task 3.5 — Beads integration.** [1h]
Create a `bd` issue template for walk-forward regressions. Auto-file when stressed pass rate drops below 66% on a regenerated report.

### Week 4 — Stabilisation

**Task 4.1 — Investigate any failing windows.** [variable, up to 1 week]
First run will almost certainly fail at least one regime (most likely 2022 tech bear). For each failure:
- Document *why* (which strategy, which regime feature).
- Decide: accept (some windows must fail, that is the point), mitigate (regime-aware allocation), or fix (strategy-level filter).
- If "fix": new commit triggers re-run; do not declare done until the master report is regenerated.

**Task 4.2 — Locked OOS window verification.** [2h]
Run the OOS window separately with `--profile master --oos-only`. This is the *first time* the locked period is touched. Result is the realistic forward expectation. If it fails: do not scale capital regardless of other window results.

**Task 4.3 — Document interpretation guide.** [2h]
Add `docs/walkforward_interpretation.md` explaining: why some windows are *expected* to fail, how to read per-strategy attribution, what counts as "regime sensitivity that's acceptable" vs. "overfitting."

**Task 4.4 — Quarterly refresh calendar.** [1h]
Add to operational calendar: regenerate `walkforward_master` on the first business day of each quarter. Add windows as more data accumulates.

## 7. Risks and Mitigations

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| Alpaca historical data does not extend back to 2019 for full universe | High | Medium | Explicitly log missing-history symbols per window; treat the report as best-effort for early windows; consider supplementing with a one-time data dump from a free source (Yahoo, Stooq) for stocks-only |
| First master run shows the system fails 2022 bear badly | High | High | This is *the point of the exercise*. Document, accept that pre-2026 the system would not have been deployable in 2022, decide whether to add a market-regime allocation overlay |
| Backtest compute time is prohibitive | Medium | Low | Cache historical data once per symbol; reuse across windows. Most cost is data fetch, not simulation. Initial run ~half a day; subsequent runs <1h |
| Per-strategy attribution requires changes to `run_backtest.py` return shape | Medium | Low | The shape is already used by `run_validation_gate.py`; small extension only |
| 2019 data with current universe is anachronistic (some tickers didn't exist) | High | Medium | Document explicitly; either skip symbols with no 2019 data or note them. This is *why* universe rebuilds (Phase 1 item 2) is a follow-up |
| Walk-forward becoming "always passes" by tuning to it | Critical | Critical | The locked OOS window guards against this. Plus: never refresh the walk-forward more often than quarterly. Resist the urge to "fix" failing windows by tuning |
| Operator (or agent) bypasses the gate to scale capital | Medium | Critical | Document the policy in CLAUDE.md as MANDATORY. Add the gate check to the live-readiness section. Code-enforce in a future iteration |

## 8. Open Questions for Review

These need an answer before Week 1 starts:

1. **Are 30 bps stressed and 66% pass rate the right numbers?** I picked them based on retail practitioner consensus and the existing `sensitivity_levels_bps: [10.0, 20.0, 30.0]`. If you want more conservative (e.g. 50 bps as the binding constraint) say so before I lock the config schema.
2. **Do you want walk-forward to gate `bd close` on strategy-touching issues?** If yes, the pre-commit hook becomes a CI blocker, not advisory.
3. **Is 180-day window length right?** 180 days is one half-cycle; 90 days catches more regimes but is statistically thinner; 252 days (one year) is more stable but reduces window count. I recommend 180 — confirm.
4. **What's the procurement budget for better historical data?** If even $50/month for a CRSP-style historical dataset is allowed, this plan accelerates. If strictly free (Alpaca + Yahoo), the early-window symbols are limited.
5. **Do you want the agent to auto-regenerate quarterly, or is this a manual scheduled task?** The schedule MCP supports this; default is auto unless you say otherwise.

Six months from now, when someone (you, me, or anyone reviewing) asks "is this system safe to run at $100k+?", the answer is no longer "the backtest says +20%." That sentence — backed by a regenerable report — is the difference between professional-grade retail and small-shop institutional. This plan exists to produce it.
